Theory
RabbitMQ kya hai — aur kyun chahiye?
Problem: Tere user creates an announcement → ab email bhejna hai, notification push karni hai, analytics log karni hai.
Ye sab synchronously kiya toh response slow ho jayega. Koi ek service crash kari toh poora request fail. 😵
Solution — Message Queue: Producer (NestJS service) sirf message queue mein daalta hai, aur wapas aa jaata hai instantly.
Consumer (doosri service / worker) apni speed se message uthata hai aur process karta hai. Decoupled! ✅
Sochna aise: RabbitMQ = ek post-office 📬. Tum letter daalo (publish) aur chale jao. Postman (consumer) apni speed se deliver karta hai. Tum wait nahi karte.
Architecture
4 Core Concepts — Exchange, Queue, Binding, Routing Key
Producer (NestJS) ──publish──▶ [Exchange] ──routing key──▶ [Queue] ──deliver──▶ Consumer Exchange Types: direct → routing key exact match chahiye (point-to-point) fanout → sab queues ko broadcast (routing key ignore) topic → pattern matching e.g. "user.*" or "*.created" headers → message headers se route (rare use) Binding = Queue ko Exchange se connect karna with routing key
Real example: announcement.created routing key publish karo → email-queue aur notification-queue dono bind hain → dono consumers independently process karenge!
Theory
Acknowledgements — Message safely process hua kaise confirm karein?
ACK (Acknowledge): Consumer message process karne ke baad RabbitMQ ko bolta hai "bhai le liya, queue se hata do".
NACK (Negative Ack): Consumer bolta hai "process nahi hua" → RabbitMQ message wapas queue mein daal deta hai (ya DLQ mein).
Gotcha: Auto-ack on kiya toh message queue se instantly hat jaata hai — chahe consumer crash ho jaye! ❌ Always use manual ack in production. 
// NestJS mein manual ack kaise karte hain
@EventPattern('announcement.created')
async handleAnnouncementCreated(
  data: AnnouncementCreatedEvent,
  @Ctx() context: RmqContext,
) {
  const channel = context.getChannelRef();
  const originalMsg = context.getMessage();
  try {
    await this.emailService.sendEmail(data);
    channel.ack(originalMsg);       // ✅ success → queue se hata do
  } catch (err) {
    channel.nack(originalMsg);      // ❌ fail → DLQ mein bhejo
  }
}

// announcements.service.ts
@Injectable()
export class AnnouncementsService {
  constructor(
    @Inject('ANNOUNCEMENT_SERVICE')
    private readonly client: ClientProxy,
  ) {}

  async create(dto: CreateAnnouncementDto) {
    const announcement = await this.repo.save(dto);

    // emit = fire and forget (event)
    this.client.emit('announcement.created', {
      id: announcement.id,
      title: announcement.title,
      createdAt: new Date().toISOString(),
    });

    return announcement;
  }
}
emit() vs send(): emit() = fire-and-forget event (response wait nahi karta). send() = request-reply pattern, Observable return karta hai. Events ke liye emit use karo!

    data: AnnouncementCreatedEvent,
    @Ctx() ctx: RmqContext,
  ) {

    await this.emailService.send(data);  // service call, DB directly nahi!
    ctx.getChannelRef().ack(ctx.getMessage());
  }

  // ✅ MessagePattern — reply chahiye (e.g. get user info)
  @MessagePattern({ cmd: 'get_user' })
  getUser(id: string) {
    return this.userService.findById(id);  // return value → caller ko milega
  }
}
Theory
Command vs Event — Sabse Important Difference
CommandEvent
Intent"Kuch karo" (imperative)"Kuch hua" (past tense)
ExampleCreateAnnouncementCommandAnnouncementCreatedEvent
ConsumersExactly 1 handler0 to N handlers (broadcast)
NamingVerb + Noun (imperative)Noun + Verb (past)
FailureCaller ko error milti haiSilent fail possible
CouplingTightly coupled (knows target)Loosely coupled (no target)
Sochna aise: Command = order dena "Ek chai bana!" (1 person responsible). Event = news announce karna "Chai ban gayi!" (sab sun sakte hain, koi bhi react kare ya na kare).

Theory
Kab Command, kab Event use karein?
✅ Command use karo jab: Kisi ek specific service ko kuch karne ke liye bol rahe ho. E.g., "UserService, password reset karo" → ResetPasswordCommand
✅ Event use karo jab: Kuch hua hai aur multiple services interested ho sakti hain. E.g., user ne signup kiya → email service, analytics service, welcome notification — sab react kar sakti hain.
❌ Event ko Command ki tarah mat use karo: SendEmailEvent → Wrong! Ye imperative hai. Sahi hai AnnouncementCreatedEvent → email service khud decide kare ki email bhejna hai.
Theory
CQRS kya hai — Command Query Responsibility Segregation
Core Idea: Write operations (Commands) aur Read operations (Queries) ko alag-alag handlers mein separate karo.

Why? Reads aur Writes ki requirements alag hoti hain — reads fast chahiye (cache-friendly), writes consistent chahiye (business logic heavy). Ek hi service mein dono mix karoge toh dono suffer karenge.
Controller │ ├──▶ CommandBus.execute(new CreateAnnouncementCommand(...)) │ └──▶ CreateAnnouncementHandler (write DB, publish event) │ └──▶ QueryBus.execute(new GetAnnouncementsQuery(...)) └──▶ GetAnnouncementsHandler (read DB / cache)
Sochna aise: Restaurant mein waiter (controller) → ya kitchen ko order deta hai (CommandHandler — sirf banata hai), ya billing ko query karta hai (QueryHandler — sirf info deta hai). Dono ke kaam alag!

CommandHandler likhna — CreateAnnouncement
// handlers/create-announcement.handler.ts
import { CommandHandler, ICommandHandler, EventBus } from '@nestjs/cqrs';

@CommandHandler(CreateAnnouncementCommand)
export class CreateAnnouncementHandler
  implements ICommandHandler<CreateAnnouncementCommand> {

  constructor(
    private readonly repo: AnnouncementRepository,
    private readonly eventBus: EventBus,
  ) {}

  async execute(command: CreateAnnouncementCommand) {
    const { title, content, authorId } = command;

    // 1. DB mein save karo
    const announcement = await this.repo.create({ title, content, authorId });

    // 2. Domain event publish karo (EventBus internally handle karega)
    this.eventBus.publish(
      new AnnouncementCreatedEvent(
        announcement.id,
        announcement.title,
        announcement.authorEmail,
        new Date(),
      )
    );

    return announcement;
  }
}

// Controller mein use karo
@Post()
create(@Body() dto: CreateAnnouncementDto) {
  return this.commandBus.execute(
    new CreateAnnouncementCommand(dto.title, dto.content, dto.authorId)
  );
}
Flow samjho: Controller → CommandBus.execute() → CreateAnnouncementHandler → DB save → EventBus.publish() → AnnouncementCreatedHandler → EmailService.send(). Clean chain! ⛓️

Theory
Dead Letter Queue (DLQ) kya hoti hai?
Problem: Consumer baar baar ek message process karne mein fail ho raha hai (e.g., email service down hai).
Normal queue mein woh message infinitely retry hoga → baaki messages block ho jayenge. 💀
Solution — DLQ: Ek separate "dead letter" queue define karo. Jab koi message N retries ke baad bhi fail ho, RabbitMQ usse DLQ mein move kar deta hai.
Main queue unblock ho jaati hai. DLQ ke messages baad mein manually inspect karo ya alert set karo.
Main Queue ──▶ Consumer [FAIL × 3] └──▶ Dead Letter Exchange └──▶ DLQ (announcement.dead) └──▶ Alert / Manual Review / Replay
Code
DLQ setup karna RabbitMQ mein
// Queue define karte waqt DLX specify karo
app.connectMicroservice({
  transport: Transport.RMQ,
  options: {
    urls: ['amqp://localhost:5672'],
    queue: 'announcement_queue',
    queueOptions: {
      durable: true,
      arguments: {
        // Fail messages yahan bhejo
        'x-dead-letter-exchange': 'announcement.dead',
        'x-dead-letter-routing-key': 'announcement.dead',
        // Optional: max retry count
        'x-message-ttl': 60000,   // 60 sec baad DLQ mein
      },
    },
    noAck: false,
  },
});
Gotcha: DLQ khud automatically create nahi hoti! RabbitMQ Management UI mein manually create karo ya consumer startup pe assertQueue call karo.
Code
Retry strategy — exponential backoff manually implement karo
@EventPattern('announcement.created')
async handleWithRetry(data: any, @Ctx() ctx: RmqContext) {
  const channel = ctx.getChannelRef();
  const msg = ctx.getMessage();

  // headers se retry count nikalo
  const retryCount = (msg.properties.headers['x-retry-count'] ?? 0);

  try {
    await this.emailService.send(data);
    channel.ack(msg);  // ✅
  } catch (err) {
    if (retryCount < 3) {
      // Requeue with incremented retry count
      channel.nack(msg, false, false);  // requeue=false → DLX pe jayega
    } else {
      console.error('❌ Max retries exceeded, moving to DLQ', err);
      channel.nack(msg, false, false);
    }
  }
}
Theory
Idempotency kya hai — aur kyun zaruri hai?
Definition: Ek operation idempotent hai agar usse ek baar ya 100 baar chalao — result same ho. Side effects duplicate nahi hone chahiye.
Real scenario: Network glitch ke wajah se RabbitMQ same message 2 baar deliver kar deta hai (at-least-once delivery guarantee). Agar tera consumer idempotent nahi hai → 2 emails jayenge, 2 DB rows banengi. 💸
Sochna aise: ATM machine idempotent hai — ek hi transaction 2 baar process nahi hoti chahe button 10 baar dabaao. Tera event consumer bhi aisa hona chahiye.
Code
Idempotency implement karna — eventId track karo
// processed_events table: id (PK), event_id (unique), processed_at

@EventPattern('announcement.created')
async handleIdempotent(data: AnnouncementCreatedEvent, @Ctx() ctx: RmqContext) {
  const channel = ctx.getChannelRef();
  const msg = ctx.getMessage();

  // 1. Pehle check karo — ye event pehle process hua tha kya?
  const alreadyProcessed = await this.processedEventsRepo.findOne({
    where: { eventId: data.announcementId }
  });

  if (alreadyProcessed) {
    console.log('⚠️ Duplicate event, skipping', data.announcementId);
    channel.ack(msg);  // ack karo taaki retry na ho
    return;
  }

  // 2. Process karo
  await this.emailService.sendNewAnnouncementEmail(data);

  // 3. Mark as processed
  await this.processedEventsRepo.save({
    eventId: data.announcementId,
    processedAt: new Date(),
  });

  channel.ack(msg);
}
Pro tip: Har event mein unique eventId ya correlationId include karo publisher side pe. Consumer isko idempotency key ki tarah use karega. UUID v4 kafi hai!
Gotcha: Never event consumer ke andar directly this.repo.save() call karo — always apni service layer use karo. Event consumer sirf orchestrate kare, business logic service mein hogi.
Theory
Redis se fast idempotency check
// DB se pehle Redis check karo — faster!
async isAlreadyProcessed(eventId: string): Promise<boolean> {
  const key = `processed:event:${eventId}`;
  const exists = await this.redis.get(key);
  if (exists) return true;

  // SET with NX (only if not exists) + expire 24h
  await this.redis.set(key, '1', 'EX', 86400);
  return false;
}
