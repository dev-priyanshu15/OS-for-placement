Day 4 — API Design: DTOs, Validation & Swagger

class-validator · class-transformer · OpenAPI · Contracts Lib

Theory

DTO kya hota hai — aur kyun zaroori hai?

DTO (Data Transfer Object) → sirf ek plain class hai jo define karta hai "is request mein kya aana chahiye"

Controller → req.body directly mat use karo, DTO inject karo

Validation → DTO ke upar decorators lagate hain, NestJS automatically validate karta hai

Type Safety → TypeScript types milti hain + runtime validation bhi

Separation of Concerns → Entity alag, DTO alag — entity = DB shape, DTO = API shape

Request DTO → CreateUserDto, UpdateUserDto (client se aata hai)

Response DTO → UserResponseDto (client ko bhejte hain, sensitive fields exclude)

Sochna aise: Entity = DB ka blueprint. DTO = API ka contract. Dono ko mix mat karo — ek din password field response mein leak ho jayegi 💀

Theory

class-validator — sabse important decorators

@IsString() → string hona chahiye

@IsEmail() → valid email format check karta hai

@IsEnum(MyEnum) → enum ke values mein se hona chahiye

@IsOptional() → field missing ho toh skip karo validation

@IsNotEmpty() → empty string allowed nahi

@IsInt() / @IsNumber() → number type check

@Min(n) / @Max(n) → numeric range

@MinLength(n) / @MaxLength(n) → string length

@IsBoolean() → true/false only

@IsDate() → valid Date object

@IsUUID() → UUID format check

@IsArray() → array hona chahiye

@ValidateNested() → nested object ke andar bhi validate karo

@IsIn(['a','b']) → specific values mein se hona chahiye

Custom Validator

@IsFutureDate() — custom decorator banana

// decorators/is-future-date.decorator.ts import { registerDecorator, ValidationOptions, ValidationArguments } from 'class-validator'; export function IsFutureDate(validationOptions?: ValidationOptions) { return function(object: Object, propertyName: string) { registerDecorator({ name: 'isFutureDate', target: object.constructor, propertyName, options: validationOptions, validator: { validate(value: any) { if (!(value instanceof Date)) return false; return value > new Date(); // future mein honi chahiye }, defaultMessage(args: ValidationArguments) { return `${args.property} future date honi chahiye!`; }, }, }); }; } // Use kaise karein export class CreateEventDto { @IsFutureDate() @Type(() => Date) // string → Date convert karta hai scheduledAt: Date; }
Test karna mat bhoolna: valid date, past date, aur non-date (string/null) — teeno cases cover karo unit test mein.
Theory

class-transformer — plain object ↔ class instance

@Type(() => SomeClass) → nested object ko class instance mein convert karo

@Expose() → sirf ye field response mein include karo

@Exclude() → ye field response se hata do (e.g. password)

@Transform() → custom transformation function

plainToInstance() → plain JSON → class instance (with @Expose/@Exclude applied)

instanceToPlain() → class instance → plain object

excludeExtraneousValues: true → sirf @Expose wale fields rakhta hai

Fail Fast Principle: validation boundary pe karo — controller mein, service ke andar nahi. Service ko assume karna chahiye ki data already valid hai.
Code

Response DTO — password field hide karna

// users/dto/user-response.dto.ts import { Exclude, Expose } from 'class-transformer'; import { ApiProperty } from '@nestjs/swagger'; export class UserResponseDto { @Expose() @ApiProperty() id: string; @Expose() @ApiProperty() name: string; @Expose() @ApiProperty() email: string; @Exclude() // password KABHI response mein nahi jayegi password: string; constructor(partial: Partial<UserResponseDto>) { Object.assign(this, partial); } } // Service mein use karna async findOne(id: string): Promise<UserResponseDto> { const user = await this.userRepo.findOne({ where: { id } }); return plainToInstance(UserResponseDto, user, { excludeExtraneousValues: true, }); }

Theory

Shared API Contracts — FE + BE ek hi DTO use kare

Problem: FE aur BE mein same DTO alag-alag likhte hain → sync issues aate hain

Solution: libs/api/contracts/ mein shared DTOs rakho

Monorepo (Nx/Turborepo) mein ye aasaan hai — same codebase share hoti hai

Separate repos? → npm package publish karo ya git submodule use karo

Benefit: Backend DTO update kiya → Frontend automatically TypeScript error deta hai

Type safety end-to-end → runtime surprises drastically kam ho jaate hain

Real world: tRPC ya OpenAPI generated clients bhi ye hi kaam karte hain — lekin manually shared DTOs simpler starting point hai.

Theory

Pagination — offset vs cursor

Offset-based: ?page=2&limit=10 → OFFSET 10 LIMIT 10 — simple, familiar

Cursor-based: ?cursor=xyz&limit=10 → last item ki ID se shuru karo — fast, consistent

Offset problem: data insert ho toh same record dobara aa sakta hai ya skip ho sakta hai

Cursor better kab: real-time data, infinite scroll, large datasets

Offset better kab: admin panels, fixed pages, small datasets

Code

Offset-based PaginationDto

// common/dto/pagination.dto.ts import { IsOptional, IsInt, Min, Max } from 'class-validator'; import { Transform } from 'class-transformer'; import { ApiPropertyOptional } from '@nestjs/swagger'; export class PaginationDto { @ApiPropertyOptional({ default: 1 }) @IsOptional() @Transform(({ value }) => parseInt(value)) @IsInt() @Min(1) page: number = 1; @ApiPropertyOptional({ default: 10 }) @IsOptional() @Transform(({ value }) => parseInt(value)) @IsInt() @Min(1) @Max(100) limit: number = 10; get skip(): number { return (this.page - 1) * this.limit; } } // Service mein use karna async findAll(pagination: PaginationDto) { const [data, total] = await this.repo.findAndCount({ skip: pagination.skip, take: pagination.limit, }); return { data, total, page: pagination.page, limit: pagination.limit }; }

Cursor-based PaginationDto

export class CursorPaginationDto { @ApiPropertyOptional({ description: 'Last item ka UUID' }) @IsOptional() @IsUUID() cursor?: string; @ApiPropertyOptional({ default: 10 }) @IsOptional() @Transform(({ value }) => parseInt(value)) @IsInt() @Min(1) @Max(50) limit: number = 10; } // Service mein cursor query async findAll({ cursor, limit }: CursorPaginationDto) { const where = cursor ? { id: MoreThan(cursor) } : {}; const data = await this.repo.find({ where, take: limit + 1, order: { id: 'ASC' } }); const hasMore = data.length > limit; if (hasMore) data.pop(); return { data, nextCursor: hasMore ? data[data.length - 1].id : null }; }
Theory

API Versioning — breaking changes handle karna

URI versioning: /v1/users, /v2/users — sabse common, visible, easy to test

Header versioning: Accept-Version: 2 — clean URLs lekin harder to test

Query param: ?version=2 — simple lekin dirty URLs

MediaType: Accept: application/vnd.api.v2+json — purist approach

NestJS default: VersioningType.URI — prefer karo yahi

Kab versioning karo: response shape change hoti ho, field remove ho, breaking change ho

Code

URI Versioning setup

// main.ts import { VersioningType } from '@nestjs/common'; app.enableVersioning({ type: VersioningType.URI, // /v1/... /v2/... defaultVersion: '1', // version nahi diya toh v1 use karo }); // ---- Controller level versioning ---- @Controller({ path: 'users', version: '1' }) export class UsersV1Controller { // /v1/users @Get() findAll() { return { data: [], version: 'v1' }; } } @Controller({ path: 'users', version: '2' }) export class UsersV2Controller { // /v2/users — new response shape @Get() findAll() { return { items: [], meta: { total: 0 }, version: 'v2' }; } } // ---- Route level versioning ---- @Controller('posts') export class PostsController { @Get() @Version('1') findAllV1() { ... } @Get() @Version('2') findAllV2() { ... } }
